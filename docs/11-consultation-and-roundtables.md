# 咨询与圆桌研讨

本页定义 AgentDesk V1 的执行前咨询契约。它用于在任务卡生成之前获得独立专业意见，帮助 Owner 看清前提、风险与分歧。

> 咨询是可选、只读的 advisory workflow。它与 `docs/pm/state/tasks.yaml`、Active roles 和执行看板正交，不改变任何执行任务状态，也不授予实施权限。

对于仓库之外的一般复杂话题，也可以使用同样的席位、授权、首轮独立、主动回调和两轮上限；这种 conversation-only 模式只在 Leader 会话交付综合，不创建项目记录，也不得声称具备 Git 审计、恢复或任务卡血缘。

## 1. 能做什么，不能做什么

咨询可以：

- 从一个到三个专业视角独立分析同一议题；
- 发现隐含假设、风险、反例和替代方案；
- 让 Leader 汇总共识、条件共识、分歧和少数意见；
- 在 Owner 决策前减少任务卡方向返工。

咨询不能：

- 修改业务代码、控制面、`tasks.yaml` 或 Active roles；
- 直接写入正式决策或生成任务卡；
- 用多数票替代 Owner 决策；
- 授权创建执行岗位会话、派发、实施、合并、部署或发布；
- 证明宿主强制使用了某个模型，或证明发言者在现实组织中具有 Owner 权限。

只有 Owner 明确确认咨询结论后，Leader 才能把确认范围写入决策记录或据此生成任务卡。后续所有执行动作仍需经过各自独立门禁。

## 2. 席位数怎样选择

V1 接受 0–3 席。0 表示明确跳过圆桌，因此不创建咨询会话；一次真实圆桌创建 1–3 个席位。

| 席位数 | 何时使用 | 典型例子 |
| ---: | --- | --- |
| 0 | 需求清楚、风险低、没有值得外部核查的问题 | 已确认的小型文案修正 |
| 1 | 问题集中在一个专业领域，需要快速独立复核 | 隐私条款、数据库索引、定价逻辑核查 |
| 2 | 需要两个互补视角或刻意制造建设性张力 | 产品价值与工程成本、增长与合规 |
| 3 | 跨多个领域、影响较大或存在明显未知项 | 产品、架构、安全共同评估重大能力 |

不要为了“更像圆桌”固定创建三席。席位必须分别回答一个有必要、可区分的问题；没有新增视角时应减少席位。

## 3. 身份与精确命名

咨询席是一次性临时身份，不写入 `ROLES.md` 的 Active roles。标题格式为：

```text
<consultation_id>.<两位席号> . <顾问岗位>｜<短议题>
```

示例：

```text
C001.01 . 产品顾问｜短议题
C001.02 . 技术顾问｜短议题
C001.03 . 风险顾问｜短议题
```

格式要求：

- consultation ID 使用 `C001`、`C002` 这类稳定编号；
- 席号使用 `.01`、`.02`、`.03`；
- 分隔点号两侧各有一个 ASCII 空格；
- 顾问岗位与短议题之间使用全角竖线 `｜`；
- 实际标题必须逐字匹配计划标题，不能用自动摘要或会话内容代替。

咨询编号不得复用；同一次咨询的第二轮继续使用原席位身份，不新建另一组编号来掩盖重试。

## 4. 授权门禁

Leader 可以在未获授权时分析是否值得咨询、提出席位方案和准备问题，但不能创建用户可见咨询会话。建议先向 Owner 展示：

- consultation ID 和短议题；
- 计划创建的 1–3 个精确会话标题；
- 每席职责和为什么需要它；
- 最多两轮、第一轮独立、中心辐射、只读等边界；
- 宿主当前能够和不能够验证的事项。

可复制的创建授权提示词：

```text
我授权为咨询 C001 创建以下 3 个用户可见、彼此独立的咨询会话：

C001.01 . 产品顾问｜短议题
C001.02 . 技术顾问｜短议题
C001.03 . 风险顾问｜短议题

本次仅进行只读 advisory 分析，第一轮各席独立，所有通信经 Leader，最多两轮。
每席完成后必须主动回调 Leader。
此授权不允许写正式决策、生成任务卡，也不授权任何执行岗位会话、实施、合并、部署或发布。
```

Leader 应将这条消息视为显式治理输入，但不能声称平台已经验证发言者的现实身份、职务或法定授权。项目对高风险事项另有身份验证或审批渠道时，仍必须使用该渠道。

记录中的授权/确认 ID 分别使用 `CA-C001-<随机大写字母数字>` 和 `CC-C001-<随机大写字母数字>`；`XXXX`、`TODO` 等模板占位符不能落盘。actor 写为 `User`、`Owner`，或带稳定标识的 `User:<id>` / `Owner:<id>`；suffix 必须含字母或数字，不能写成 `TODO`、`TBD`、`XXXX`、`pending`、`unbound` 或 `placeholder`。Leader 不能把自己写成授权者或确认者。

## 5. 标准运行流程

### 第 0 步：决定是否咨询

Leader 判断需要 0、1、2 或 3 席。选择 0 时记录“跳过咨询”的理由即可，不创建会话、不伪造咨询结果，正常进入需求确认流程。

### 第 1 步：提出计划并等待授权

Leader 分配 consultation ID，给出席位、精确标题、共同事实包、席位问题和边界，等待用户明确授权创建这些会话。项目记录此时必须保持 `awaiting_authorization`、`creation_authorization: null`、席位 `planned`、`rounds: []`；模板不会预填一条并不存在的授权。

### 第 2 步：创建、命名与读取复验

在宿主提供任务工具时，逐席创建独立会话、设置精确标题并读取复验。咨询席必须与 Leader、其他咨询席和 Active 执行岗位使用不同会话身份。

如果宿主无法读取真实会话或核对标题，只能披露“会话/标题未验证”。不能用逻辑标签、同会话人格切换或一段模拟对话声称已经完成独立圆桌。

### 第 3 步：第一轮独立作答

Leader 给每席发送同一份经过冻结的共同事实，并附该席专属问题。第一轮必须满足：

- 咨询席看不到其他席的答案；
- 咨询席之间不直接通信；
- Leader 不在收齐前把某席结论透露给其他席；
- 每席明确给出结论、成立条件、证据/假设、风险和未知项；
- 每席主动向 Leader 来源会话回调。

咨询席只在自己的会话输出 final answer，不算主动回调。宿主不支持跨会话回调时，应明确说明能力缺口，不能宣称完整 V1 圆桌已经闭环。

Round 1 使用 `assets/consultation-response-template.md`。它不包含第二轮占位块，按模板完成后可以直接通过首轮 artifact 校验。

### 第 4 步：Leader 首轮综合

Leader 不按“二比一”投票，而按以下结构整理：

1. **共识**：各席在主要事实和建议上相容；
2. **条件共识**：结论只在明确条件成立时相容；
3. **分歧**：前提、目标、证据权重或风险容忍度发生冲突；
4. **少数意见**：即使只有一席提出，也必须保留的高价值反例或风险；
5. **未验证项**：缺少数据、宿主证据或外部批准，当前不能裁决。

### 第 5 步：可选第二轮

只有首轮出现会影响 Owner 决策的明确冲突或缺口时才开启第二轮。Leader 把中性或匿名化的分歧摘要分别转述给所有原席位，仍保持中心辐射，不允许席位直接辩论。

第二轮结束后必须停止。仍无法解决的事项作为分歧、少数意见或未验证项交给 Owner，不能通过第三轮拖延，也不能用多数票消除。

进入第二轮前，Round 1 必须已经收口：所有已收到回答已持久化，且第二轮最早 prompt 不能早于任一 Round 1 callback receipt。

Round 2 使用单独的 `assets/consultation-response-r2-template.md`，必须把 `unchanged | narrowed | changed` 替换为一个明确值并说明原因。

### 第 6 步：向 Owner 提交综合结果

Leader 给出：

- 议题和咨询范围；
- 实际参与席位及其回调状态；
- 共同事实与每席特殊假设；
- 共识、条件共识、分歧、少数意见和未验证项；
- Leader 的建议及其理由；
- 宿主、模型、会话、回调和授权的验证/未验证披露；
- 请 Owner 明确确认、修改、拒绝或暂缓的事项。

### 第 7 步：Owner 确认后才进入执行准备

可复制的确认提示词：

```text
我确认咨询 C001 的以下结论：<明确列出结论和适用条件>。
我授权 Leader 将这些已确认内容写入项目决策，并据此生成候选任务卡。

本确认不授权创建或复用执行岗位会话，不授权派发、实施、合并、部署或发布；这些动作仍需分别通过 AgentDesk 的后续门禁。
```

没有明确确认时，Leader 只能保留咨询综合和待决问题，不得写 `DECISIONS.md`，也不得生成任务卡。模糊回应、沉默、表情反馈或此前的项目开发授权都不能替代本次确认。

确认后派生任务卡时，卡片 frontmatter 必须同时包含：

```yaml
source_consultation_id: C001
source_confirmation_id: CC-C001-2D91
```

咨询记录的 `derived_refs.task_card_paths` 反向列出该卡。派生决策日志行同样同时引用 consultation ID 和 confirmation ID；这样 validator 才能证明不是一张脱离确认范围的“未链接任务卡”。

## 6. 模型建议与宿主披露

模型选择以议题难度和席位职责为准，不以席位数量机械决定：

| 职责 | 建议 |
| --- | --- |
| 单领域席位 | 对口能力，通常建议 `advanced / balanced` |
| 反方、风险或高不确定席位 | 强反例分析，通常建议 `advanced / deep`；高风险可建议 `expert / deep` |
| Leader 综合 | 能比较不同前提并保留冲突；高不确定性可建议 `expert / deep` |

这些只是建议。V1 咨询不把执行任务的九字段模型快照套到咨询席，也不声称 `ROLE-POLICIES.yaml` 自动约束咨询会话。只有用户明确要求某个精确模型且宿主支持精确 override 时，Leader 才应传入该 override；其他情况省略 override。本机 `model_binding` 区分 `default_unverified`、`override_unverified` 与 `verified`，但只在宿主返回可信、可读取的实际执行证据，且 actual model 与精确请求逐字相等时才可使用 `verified`；否则应写“请求模型为……，实际模型未验证”。

每次综合至少披露以下状态：

| 事项 | 可接受表述 |
| --- | --- |
| 会话存在且独立 | 已由宿主读取验证 / 未验证 |
| 精确标题 | 已读取匹配 / 未验证或不匹配 |
| 第一轮隔离 | 由编排流程保证 / 宿主不能独立证明 |
| 主动回调 | 已观察送达 / 发送结果不明 / 缺失 |
| 实际模型 | 有可信宿主证据 / 未验证 |
| Owner 身份与授权 | 收到显式用户确认 / 现实身份与权限未由平台验证 |

## 7. 故障与恢复

| 故障 | 恢复方式 | 禁止做法 |
| --- | --- | --- |
| 尚未授权创建咨询会话 | 保持计划态，展示精确席位清单并等待授权 | 从“开始讨论”推定创建权限 |
| 会话缺失或标题错误 | 停止该席，修正标题并读取复验；不能验证则披露 | 用逻辑标签冒充真实席位 |
| 第一轮答案互相污染 | 将受影响席标记为非独立，必要时在原咨询内重跑该轮或保留缺陷 | 隐瞒污染并宣称独立圆桌 |
| 席位超时或失联 | 保存已有材料，重试原席位；仍失败则以覆盖缺口结束 | 静默替换为未披露的模拟意见 |
| 席位只在本会话输出、没有主动回调 | 使用同一咨询/席位身份重试回调；仍失败则标记 callback missing | 由 Leader 扫描结果冒充主动回调 |
| Leader route 不可用 | 暂停收口并修复来源路由 | 让席位互相发送或自行形成决议 |
| 宿主不支持独立会话或跨会话消息 | 选择 0 席，或明确降级为人工咨询并披露“不构成完整 V1 圆桌” | 同会话切换人格后声称创建了 1–3 席 |
| 两轮后仍有分歧 | 原样交给 Owner，附条件和少数意见 | 开第三轮或按票数强行裁决 |
| Owner 未明确确认 | 保持 advisory 状态 | 写正式决策、生成任务卡或开始执行 |
| 研讨中途取消 | 写明 `cancellation_reason`，保留已发生轮次、回答和 receipt；派生引用保持为空 | 删除第二轮或回调证据来迁就终态 |

恢复永远复用原 consultation ID 和席位身份。只有开始一个不同议题时才分配新的 consultation ID。

## 8. `CONSULTATIONS.md` 的权威边界

每次真实咨询的公开生命周期权威是：

```text
docs/pm/consultations/CNNN/consultation.yaml
```

它只裁决该次 advisory lifecycle，不能驱动或覆盖执行状态。咨询的真实 task/thread ID、标题读取结果、prompt receipt 和 response receipt 保存在 gitignored `.agentdesk/runtime/consultations.yaml`，不得复制进公开记录或视图。

`CONSULTATIONS.md` 由公开 consultation records 动态生成，是只读投影，可以展示：

- consultation ID、短议题和公开生命周期状态；
- 已声明的席位数与轮次记录数；
- outcome、Owner confirmation、综合报告与派生引用状态；
- 公开记录的最后更新时间。

它不读取 `.agentdesk/runtime/consultations.yaml`，因此不展示或证明实时会话存在性、actual title、prompt 送达或 callback receipt。需要这些结论时必须另行执行当次 provider read/list 与 runtime 校验。

它不能成为：

- 咨询创建授权或 Owner 身份证明；
- 正式产品决策；
- `tasks.yaml`、任务卡或 Active role 的替代来源；
- 派发、实施、验收、合并、部署或发布授权；
- transport receipt、会话 ID、绝对路径或其他运行时秘密的公开副本。

该文件即使被提交，也只是某一时刻的生成快照，禁止手工编辑。缺失、过期或被删除不会改变 consultation record 或执行权威状态；发现与真实会话、Owner 明确确认或正式决策冲突时，应标记投影失效并从公开记录重新生成，必要时再用运行时证据对账，不能反向修改权威事实来迁就视图。

公开 consultation records 更新后使用已有视图命令重新生成：

```bash
python3 <skill-dir>/scripts/render_views.py --project <repo>
```

生成器会先运行公开咨询严格校验；缺字段、非法状态、时间因果倒置或派生血缘不自洽时，它会拒绝生成 `CONSULTATIONS.md`，不会把无效 record 投影成“已关闭”。

校验也会拒绝只有章节标题、仍含 `<TBD>` / `TODO` / `XXXX` / 模板 `<...>` token 的 brief、response 或 synthesis。公开 record 和 artifact 的自由文本不得包含运行时 ID/凭据键值或本机绝对路径；provider evidence 对象如果带状态，必须是对应证据类型的明确终态成功，不接受 `pending`、`queued`、`timeout` 或 `unknown`。

随后校验公开生命周期和产物：

```bash
python3 <skill-dir>/scripts/validate_consultations.py --project <repo>
```

如果已经创建过真实咨询会话，再执行运行时门禁：

```bash
python3 <skill-dir>/scripts/validate_consultations.py --project <repo> --require-runtime
```

默认校验只回答“公开记录是否自洽”；`--require-runtime` 进一步核对本机保存的 Leader/席位 route、精确标题、席位创建时间与终态创建证据、prompt receipt 与 response receipt。prompt receipt 必须用 SHA-256 绑定当轮公开 brief 字节，response receipt 必须通过同席同轮的 `prompt_id + response_id` 关联并绑定公开 response 字节；时间因果要求授权早于席位创建/验证，brief 与席位验证都早于 prompt，prompt 早于主动回调，回调早于 Leader 持久化公开回答，随后才是综合与 Owner 确认，所有事件均不晚于公开记录更新时间。brief 可以预先准备，但未授权不得建席，未发送不得接纳回答。二者都不能证明宿主此刻的真实状态或 provider 当时实际传输了完全相同的 payload，最终收口前仍需通过宿主的 read/list/message 能力实时复验会话存在性、标题、发送与回调送达。

咨询不进入执行 Kanban 列、任务 WIP、Active role 数量或任务完成率。产品界面如需展示，应从导航进入独立咨询视图，而不是把咨询卡嵌进执行看板；不得让咨询席伪装成 Worker、让咨询完成伪装成任务完成，或通过拖拽咨询卡改变执行状态。

## 9. 最小完整示例

一个重大导出功能准备立项时，Leader 选择三席：

```text
C001.01 . 产品顾问｜批量导出
C001.02 . 架构顾问｜批量导出
C001.03 . 安全顾问｜批量导出
```

第一轮分别回答用户价值、系统负载、数据泄露风险，不看其他席答案。Leader 收到三次主动回调后，识别出：

- 共识：需要异步导出；
- 条件共识：仅在有任务过期和并发限制时开放批量能力；
- 分歧：首版是否支持 PDF；
- 少数意见：导出文件下载链接可能造成越权；
- 未验证项：真实峰值数据量。

第二轮只追问 PDF 对性能和权限面的影响。Leader 收口后请 Owner 明确确认。Owner 确认的内容才能进入决策和候选任务卡；是否创建前端、后端、QA 执行岗位任务，仍需要之后单独授权。
